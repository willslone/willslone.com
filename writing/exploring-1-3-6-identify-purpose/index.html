Exploring 1.3.6 Identify Purpose

What’s familiar to one user isn’t familiar to another, whether it’s a word or an icon. This criterion asks pages to expose a component’s purpose so each user’s own tools can present it in terms they already recognize.

Part of the series: Exploring WCAG Level AAA

The short version: This criterion asks authors to programmatically expose the purpose of icons, page regions, and UI components, so that assistive technology and other user agents can present them using terms or symbols the user already understands.

What does 1.3.6 require?

The official language: “In content implemented using markup languages, the purpose of User Interface Components, icons, and regions can be programmatically determined.”

For regions, meeting this today is straightforward: use landmarks, either through semantic HTML elements like header, nav, main, and footer, or through ARIA landmark roles like role="search" where HTML has no native element for the job. That’s the one part of this criterion with an established WCAG technique behind it.

It’s tempting to assume a good accessible name covers 1.3.6 for an icon: a magnifying glass labeled “Search,” a hamburger labeled “Menu.” But what 1.3.6 wants is a way to expose an icon’s underlying concept, so a user agent could swap the icon itself for a different one the user already recognizes. The specification built for that, the W3C’s WAI-Adapt: Symbols Module, tags content with a concept value drawn from a shared registry of symbols used in AAC (augmentative and alternative communication). A user agent can then render a person’s preferred symbol set in place of whatever icon a site shipped with. The module has reached Candidate Recommendation status, further along than most of WAI-Adapt, but the spec’s own text notes that its examples are illustrative because implementations aren’t final.

The scope covers more than icons already on the page. WCAG’s own supporting materials describe a gamer with a language-processing disability who runs software that turns navigation text into symbols. A plain text link reading “Home” could carry the same kind of concept information as an icon, so that software renders a house symbol in place of the word. Picture or word, the ask is the same: expose the concept behind it so a user agent can act on it.

How 1.3.6 relates to 1.3.5

1.3.5 Identify Input Purpose has a narrow scope: input fields that collect information about the user, such as name, email, and address. WCAG defines a fixed list of recognized input purposes, and you meet the criterion by using the matching autocomplete attribute value on each field. It’s a bounded, well-specified requirement with a clear pass condition.

1.3.6 applies to a much broader set of content: icons, regions, and general UI components. There’s no fixed, normative list of “purposes” to check against. Today, meeting 1.3.6 comes down to landmarks for regions. For icons, the mechanism the criterion points to, exposing a concept a user agent could act on rather than just a label, exists as a specification but not yet as something most sites can implement.

Who does this help, and how?

The primary beneficiaries are people with cognitive and learning disabilities, particularly people who rely on a limited or specific vocabulary to navigate the web. That includes people who use AAC and are used to a particular set of symbols for concepts like “home,” “help,” or “search.” A site’s own iconography might use a different symbol for the same idea, and that mismatch can leave a person unable to understand the page.

It also helps people with difficulty concentrating or processing text. A personalization tool could strip a page down to the regions that matter to them. It could hide a promotional sidebar or secondary navigation and leave the main content in view.

The need varies by person and by moment. The Understanding document puts it plainly: what is familiar to one user may not be familiar to another. The W3C’s Making Content Usable for People with Cognitive and Learning Disabilities adds that similar difficulties can come from situational factors, such as an unfamiliar or noisy environment, and not only from a disability. Programmatic purpose is what makes personalization possible. Without it, a site can only offer one fixed presentation, with symbols and terms baked in at design time, regardless of who’s using it or when.

Meeting 1.3.6 exposes purpose in the markup. It doesn’t, by itself, change what a user sees. The benefit only shows up once something on the receiving end (a browser extension, an AAC tool, or a personalization agent) reads that markup and acts on it. That ecosystem exists in pieces today. Screen readers already make good use of landmark roles, but personalized symbols and terminology driven by a site’s purpose metadata depend on tools that are still emerging.

Why did this land at AAA?

I’m not aware of the working group’s reasoning behind individual placement decisions, so what follows is informed interpretation rather than inside knowledge.

Two things probably kept this out of AA. The first is scope. Unlike 1.3.5, which hands authors a specific list of input purposes and a specific attribute to use, 1.3.6 asks authors to expose purpose across an open-ended category of content (icons, regions, and components) with no normative vocabulary to check conformance against for most of it. That’s much harder to test consistently or require site-wide. The ambiguity shows up in the WCAG working group’s own GitHub repository, where an issue opened in 2023 asks how to test 1.3.6 and what would cause it to fail. It remains open and unresolved.

The second is the state of the supporting technology, especially for icons. A criterion like this depends on a two-sided ecosystem: authors adding the metadata, and user agents or assistive technology consuming it in a way that benefits the user. A criterion whose central benefit, for icons at least, depends on support that doesn’t exist yet is a reasonable fit for the highest conformance level.

Common pitfalls

Confusing this with 1.3.5

They sound alike and share a theme, but 1.3.5 is a narrow, well-defined Level AA requirement about input fields, while 1.3.6 is a broad Level AAA requirement about icons, regions, and components with no fixed list of purposes. Meeting one doesn’t mean you’ve met the other.

Confusing an icon’s accessible name with its purpose

Giving an icon a good accessible name is important, but 1.3.6 asks for something else. The name tells a screen reader what the icon means. It gives a user agent nothing to act on if the goal is swapping the icon itself for a different, more familiar one.

Assuming the personalization payoff exists today

Adding WAI-Adapt attributes to a page right now won’t change the experience for most users, because few tools that consume that metadata are deployed yet. That’s no reason to skip the landmark work that pays off today. Just set expectations with clients or stakeholders about what conforming delivers now and what it’s building toward.

Skipping landmarks because a region is visually obvious

A header looks like a header and a main content area looks like a main content area, to a sighted user. None of that is available to someone using a screen reader or a personalization tool unless the region has an actual landmark role. Visual clarity doesn’t substitute for programmatic structure.

Treating the whole criterion as having a settled pass or fail line

Only landmarks have one. WCAG documents no failures for 1.3.6, and ARIA11 is the only sufficient technique with a test procedure.

How to test it

This section is aimed at accessibility professionals performing conformance evaluations.

Scope your review to the regions of each page. Landmarks, through the ARIA11 technique, are the one part of 1.3.6 with an established technique and test procedure.

Are page regions marked up with landmarks?

Check whether major structural regions (header, navigation, main content, complementary content, footer, and search) use native HTML sectioning elements or the matching ARIA landmark roles. When a page has more than one landmark of the same type, such as two navigation regions, giving each a unique name is a best practice that helps people tell them apart.

Expected results

Pass

Major structural regions use appropriate landmark roles.

Fail

Structural regions are built from generic, unmarked containers with no landmark roles.

Automated testing and AI

Automated tools can help find regions that lack landmarks. Tools built on axe-core, such as axe DevTools with best practices turned on, flag page content that sits outside any landmark. That rule is a best practice rather than a WCAG failure condition, so treat its results as a way to locate candidates, then confirm each one by hand.

What tools can’t judge is whether a region has the right landmark type. A tool can see that a nav element exists. It can’t tell whether that region is the site’s primary navigation or a list of footer links.

AI-assisted tools can suggest where landmarks belong by analyzing a page’s layout, which can speed up a first pass. Deciding whether a suggested structure matches how the page works for a screen reader user still takes a person.
